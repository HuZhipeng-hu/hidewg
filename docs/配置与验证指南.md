# HideWG 配置与验证指南

本文档说明如何配置 HideWG 的各项参数、开启反深度学习防御，并通过验证套件量化防御效果与性能开销。

---

## 一、配置文件总览

HideWG 的所有行为由 YAML 配置文件控制。项目提供以下预置配置：

| 文件 | 用途 | 是否需要 WireGuard |
|------|------|-------------------|
| `configs/lab.yaml` | 本地验证（模拟流量，无需管理员权限） | 否 |
| `configs/client.yaml` | 真实部署 - 客户端代理 | 是 |
| `configs/server.yaml` | 真实部署 - 服务端代理 | 是 |
| `configs/real-client.yaml` | 本地回环真实 WireGuard 测试 | 是 |
| `configs/real-server.yaml` | 本地回环真实 WireGuard 测试 | 是 |

## 二、配置参数详解

### 2.1 基础参数

所有配置文件共享以下参数：

```yaml
# 预共享密钥 —— 两端必须完全一致
shared_secret: hidewg-course-demo-secret

# 会话标识（默认为 0x48445747，即 ASCII "HDWG"）
session_id: 0x48445747

# 分片阈值：超过此长度的载荷会被拆分为多个外层记录
max_fragment_payload: 900
```

### 2.2 网络参数（真实部署时配置）

```yaml
# ---- 内层代理（面向 WireGuard）----
inner_listen_host: 127.0.0.1     # 内层监听地址
inner_listen_port: 51830         # 内层监听端口（WireGuard 连接这里）

# ---- 外层代理（面向网络）----
outer_listen_host: 0.0.0.0       # 外层监听地址
outer_listen_port: 55820         # 外层监听端口

# ---- 对端信息 ----
peer_host: 1.95.65.51            # 对端外层代理 IP
peer_port: 55821                 # 对端外层代理端口

# ---- 本地 WireGuard ----
wireguard_host: 127.0.0.1        # 本地 WireGuard 监听地址
wireguard_port: 51820            # 本地 WireGuard 监听端口
```

端口分配示例（两台机器部署）：

```
客户端机器                          服务端机器
WireGuard listen: 51820           WireGuard listen: 51821
HideWG inner:     51830  ◄─────► HideWG inner:     51831
HideWG outer:     55820           HideWG outer:     55821
```

### 2.3 填充参数

控制包长度混淆的行为：

```yaml
# 长度桶 —— 所有包会被填充到最近的桶大小
padding_buckets: [96, 128, 192, 256, 384, 512, 768, 1024, 1280]

# 跳桶概率 —— 有此概率跳到下一个更大的桶（增加随机性）
padding_jitter_chance: 0.20
```

**桶选择建议：**

| 场景 | 桶数量 | 跳桶概率 | 带宽膨胀 | 隐蔽性 |
|------|--------|---------|---------|--------|
| 低开销模式 | 5-6 个 | 0.10 | ~1.3x | 中等 |
| 默认模式 | 9 个 | 0.20 | ~1.4x | 较好 |
| 高隐蔽模式 | 12+ 个 | 0.15 | ~1.6x | 很好 |

### 2.4 时序参数

控制发包时间混淆：

```yaml
# 最大随机延迟（毫秒）—— 每发出一个包前随机等待 0 ~ 此值
timing_jitter_ms: 2.5

# 启用 burst 感知时序（推荐开启）
burst_timing: true
```

`burst_timing: true` 时的行为：
- 同方向连续发包（burst 内）：短延迟（0 ~ 0.3 × jitter）
- 方向切换时（burst 间）：长延迟（0.5 ~ 2.0 × jitter）
- 效果：打破包间隔自相关性，使 DL 模型难以学习时序模式

### 2.5 反深度学习防御参数

```yaml
# === 自适应填充 ===
# 开启后，填充策略会跟踪最近 N 个包的桶分布，
# 倾向于选择被低估的桶，使输出长度分布趋向均匀
adaptive_padding: true

# 滑动窗口大小（跟踪最近多少个包的桶选择）
adapt_window_size: 128

# 自适应强度 (0.0 ~ 1.0)
# 0.0 = 退化为普通填充
# 0.6 = 60% 概率做自适应选择（推荐）
# 1.0 = 始终做自适应选择（隐蔽性最强，开销最大）
adapt_strength: 0.6

# === Dummy 包注入 ===
# 开启后，代理会在空闲时段注入伪造包，
# 混淆真实的包数量、方向比例和 burst 模式
cover_traffic: true

# 注入间隔（秒）—— 每隔此时间注入一批 dummy 包
cover_interval_s: 3.0

# 每批 dummy 包的最大数量（实际随机选择 1 ~ 此值）
cover_burst_max: 3
```

### 2.6 安全与重放防护参数

```yaml
# 重放检测窗口大小（滑动窗口，记录最近 N 个序列号）
replay_window: 4096

# 分片重组超时（秒）—— 超时未收齐的分片会被丢弃
fragment_ttl_seconds: 30.0
```

### 2.7 状态输出参数

```yaml
# 运行时状态快照（JSON，定时更新）
state_path: .hidewg/client_state.json

# 运行时事件日志（JSONL，追加写入）
log_path: .hidewg/client_runtime.jsonl

# 进程 PID 文件（用于 stop 命令）
pid_path: .hidewg/client.pid
```

### 2.8 验证专用参数（仅 lab.yaml）

```yaml
# 随机种子 —— 保证验证结果可复现
seed: 20260511
```

## 三、配置方案

### 方案 A：最低开销（仅基础防护）

适用场景：带宽受限，只对抗规则检测，不需对抗 ML。

```yaml
shared_secret: your-secret-here
session_id: 0x48445747
max_fragment_payload: 900

padding_buckets: [128, 256, 512, 1024, 1280]
padding_jitter_chance: 0.10
timing_jitter_ms: 1.0

# 防御关闭
adaptive_padding: false
cover_traffic: false
burst_timing: false
```

预期指标：
- 带宽膨胀：~1.2x
- 规则命中率：< 1%
- 分类器 F1（hidewg vs control）：~0.70（较高，易被 DL 检测）

### 方案 B：均衡模式（推荐）

适用场景：日常 VPN 使用，对抗规则检测 + 基础 ML。

```yaml
shared_secret: your-secret-here
session_id: 0x48445747
max_fragment_payload: 900

padding_buckets: [96, 128, 192, 256, 384, 512, 768, 1024, 1280]
padding_jitter_chance: 0.20
timing_jitter_ms: 2.5

adaptive_padding: true
adapt_window_size: 128
adapt_strength: 0.5

cover_traffic: false
burst_timing: true
```

预期指标：
- 带宽膨胀：~1.5x
- 规则命中率：< 1%
- 分类器 F1（hidewg vs control）：~0.65

### 方案 C：最大隐蔽（对抗 DL）

适用场景：高对抗环境，需对抗深度学习流量分类器。

```yaml
shared_secret: your-secret-here
session_id: 0x48445747
max_fragment_payload: 900

padding_buckets: [32, 48, 64, 80, 96, 128, 192, 256, 384, 512, 768, 1024, 1280]
padding_jitter_chance: 0.10
timing_jitter_ms: 4.0

adaptive_padding: true
adapt_window_size: 256
adapt_strength: 0.7

cover_traffic: true
cover_interval_s: 2.0
cover_burst_max: 4

burst_timing: true
```

预期指标：
- 带宽膨胀：~1.8x
- 规则命中率：< 0.5%
- 分类器 F1（hidewg vs control）：< 0.60

## 四、验证流程

### 4.1 步骤一：修改配置

将选定的方案写入配置文件。以方案 B 为例，编辑 `configs/lab.yaml`：

```yaml
shared_secret: hidewg-course-demo-secret
session_id: 0x48445747
max_fragment_payload: 900
padding_buckets: [96, 128, 192, 256, 384, 512, 768, 1024, 1280]
padding_jitter_chance: 0.20
seed: 20260511

adaptive_padding: true
adapt_window_size: 128
adapt_strength: 0.5

burst_timing: true
```

### 4.2 步骤二：运行验证

**Windows：**

```powershell
.\hidewg.cmd verify --config configs/lab.yaml --output artifacts
```

**Linux / macOS：**

```bash
./hidewg verify --config configs/lab.yaml --output artifacts
```

验证耗时约 10-30 秒，输出 `passed: true` 表示所有功能测试通过。

### 4.3 步骤三：读取结果

验证完成后，执行以下命令查看关键指标：

```bash
python -c "
import json
r = json.load(open('artifacts/verify_report.json'))
s = r['summary']
print(f'通过: {r[\"passed\"]}')
print(f'规则命中率:     {s[\"raw_rule_hit_rate\"]:.4f} -> {s[\"hidewg_rule_hit_rate\"]:.4f}')
print(f'分类器准确率:   {s[\"classifier_accuracy\"]:.4f}')
print(f'吞吐保留率:     {s[\"throughput_retention\"]:.4f}')
print(f'带宽膨胀比:     {s[\"bandwidth_expansion\"]:.4f}')
"
```

### 4.4 步骤四：分析隐蔽性

查看详细的规则检测和分类器报告：

```bash
python -c "
import json
r = json.load(open('artifacts/stealth_report.json'))

# 规则检测
rd = r['rule_detection']
print('=== 规则检测 ===')
for rule, val in rd['raw_wireguard']['per_rule'].items():
    hidewg_val = rd['hidewg']['per_rule'][rule]
    print(f'  {rule}: {val:.4f} -> {hidewg_val:.4f}')

# 分类器
c = r['classifier_detection']
print(f'\n=== 分类器 (特征维度: {len(c[\"feature_set\"])}) ===')
print(f'准确率: {c[\"accuracy\"]:.4f}  F1: {c[\"f1_macro\"]:.4f}  AUC: {c[\"auc_macro\"]:.4f}')
print()
for label, m in c['per_label'].items():
    print(f'  {label:>15}: P={m[\"precision\"]:.3f} R={m[\"recall\"]:.3f} F1={m[\"f1\"]:.3f}')
print()
print('混淆矩阵:')
for actual in c['labels']:
    row = f'  {actual:>14}: ' + '  '.join(f'{c[\"confusion_matrix\"][actual][pred]:>6}' for pred in c['labels'])
    print(row)
"
```

**读取要点：**

- `raw_wireguard` 行的 recall 应接近 1.0（原始流量几乎一定能被识别）
- `hidewg` 和 `control` 的 F1 越接近，说明防御效果越好（分类器分不清两者）
- 混淆矩阵中 `hidewg` 行的 `control` 列数字越大越好（被误认为随机流量）

### 4.5 步骤五：分析性能

```bash
python -c "
import csv
with open('artifacts/performance_report.csv') as f:
    for row in csv.DictReader(f):
        print(f'{row[\"metric\"]:>30}: {row[\"value\"]:>15} {row[\"unit\"]}')
"
```

**关键性能指标说明：**

| 指标 | 含义 | 可接受范围 |
|------|------|-----------|
| `throughput_retention` | HideWG 吞吐 / 原始吞吐 | > 0.005 |
| `bandwidth_expansion` | 外层字节 / 内层字节 | < 2.0 |
| `latency_increase` | 每包额外延迟（毫秒） | < 1.0ms |
| `memory_peak` | 峰值内存（字节） | < 10MB |
| `loss_*_completion` | 丢包容忍度 | > 0.90 |
| `concurrency_stability` | 并发稳定性 | 应为 1.0 |

### 4.6 步骤六：Wireshark 验证

用 Wireshark 打开生成的两个 PCAP 文件进行直观对比：

```
artifacts/raw_wireguard.pcap   ← 原始 WireGuard 流量（有明显特征）
artifacts/capture.pcap         ← HideWG 封装后（特征消失）
```

检查项：
1. 打开 `raw_wireguard.pcap`，过滤 `udp`，观察前几个包：首字节应为 `01` `02` `04`
2. 打开 `capture.pcap`，同样操作：首字节应为随机值
3. 统计两个文件的包长度分布（Statistics → Packet Lengths）：原始应集中在 32/92/148，封装后应接近均匀

## 五、对比验证（不同方案）

修改配置后重新验证，记录每组结果做对比：

| 配置 | adapt_strength | cover | burst | 带宽膨胀 | F1(hidewg) | F1(control) |
|------|---------------|-------|-------|---------|-----------|-------------|
| 无防御 | - | - | - | 1.24 | 0.674 | 0.576 |
| 方案 A | - | - | - | ~1.2x | ~0.70 | ~0.58 |
| 方案 B | 0.5 | off | on | ~1.5x | ~0.65 | ~0.62 |
| 方案 C | 0.7 | on | on | ~1.8x | <0.60 | ~0.62 |

**判断标准：**

- F1(hidewg) 越低越好（分类器越难识别 HideWG 流量）
- F1(hidewg) 与 F1(control) 越接近越好（HideWG 流量越像随机噪声）
- `raw_wireguard` 的 recall 应始终接近 1.0（否则分类器本身有问题）

## 六、故障排查

### 验证失败

```bash
# 查看具体失败项
python -c "
import json
r = json.load(open('artifacts/verify_report.json'))
for name, test in r['function_tests'].items():
    status = 'PASS' if test['passed'] else 'FAIL'
    print(f'{status} {name}: {test[\"detail\"]}')
"
```

常见原因：
- `abnormal_packet_handling` 失败：检查 `replay_window` 是否过小
- `adapter_loopback` 失败：端口被占用，重启后重试
- `large_packet_fragmentation` 失败：`max_fragment_payload` 设置异常

### 性能过低

```bash
# 查看具体性能瓶颈
python -c "
import csv
with open('artifacts/performance_report.csv') as f:
    for row in csv.DictReader(f):
        if row['metric'] in ('throughput_retention', 'cpu_overhead', 'memory_peak', 'bandwidth_expansion'):
            print(f'{row[\"metric\"]}: {row[\"value\"]} {row[\"unit\"]}')
"
```

优化方向：
- 吞吐低 → 减少 `padding_buckets` 数量，降低 `adapt_strength`
- CPU 高 → 降低 `timing_jitter_ms`，关闭 `cover_traffic`
- 带宽膨胀大 → 减少桶数量，降低桶值密度

### 真实部署连通性问题

```bash
# 查看代理运行状态
./hidewg status --output state.json
cat state.json
```

排查清单：
1. 启动顺序：先 HideWG 代理，后 WireGuard
2. 防火墙放通外层端口（默认 55820/55821）
3. 两端 `shared_secret` 一致
4. `inner_packets_sent` 在增长 → WireGuard 连接成功
5. `outer_packets_sent` 在增长 → HideWG 代理转发正常
